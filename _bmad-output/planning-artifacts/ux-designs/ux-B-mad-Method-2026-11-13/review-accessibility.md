# Accessibility Review — Rebat

## Overall verdict
The Accessibility Floor section is honest where it speaks — it correctly flags touch-target sizing, screen-reader labeling, and dynamic-type as unverified rather than claiming compliance it has no evidence for. But its one affirmative claim ("status is never color-only") is only half the story: pairing color with text doesn't guarantee legible contrast, and computing actual ratios from the DESIGN.md token table surfaces two real WCAG AA failures (status-badge-negative and status-badge-brand) that neither document catches, because contrast math falls through the crack between "visual contrast lives in DESIGN.md" (EXPERIENCE.md) and DESIGN.md never actually computing it. Several safety-critical and motor/screen-reader-relevant gaps (SOS reachability, drag-to-reorder with no alternative, un-extendable countdown timers) are either flagged as open questions or missing entirely and deserve explicit callouts before this is treated as handoff-ready.

## Findings

- **high** `status-badge-negative` fails WCAG AA for normal text (DESIGN.md Components / `status-badge-negative`, token table lines 33–38, 118–121) — `danger-default` (`#e11d48`) text on `danger-soft` (`#fff1f2`) background computes to **4.28:1**, below the 4.5:1 normal-text threshold (it clears 3:1 for large text/UI components only). This is the destructive-status badge color pairing, used for things like "Rejected"/"Cancelled" chips, and the "tightest badge text" in the system is documented at 10.5px — well into normal-text territory, not large-text. Fix: darken `danger-default` for text-on-soft use (e.g. toward `danger-strong` `#be123c`, which should clear 4.5:1) or verify the actual rendered badge font size/weight qualifies as "large text" (≥18.66px bold / ≥24px regular) before shipping as-is.

- **critical** `status-badge-brand` fails WCAG AA badly (DESIGN.md Components / `status-badge-brand`, lines 14–15, 134–137) — `accent-default` (`#16c79a`, the teal brand color) as text on `accent-soft` (`#f3fcfa`) background computes to **2.08:1** — a severe failure of even the 3:1 large-text/UI-component floor, let alone 4.5:1. Every other soft/strong badge pairing in the system passes AA (success 5.28:1, warning 4.84:1, info 4.75:1, neutral 7.38:1) because those "-default" tones are dark enough; `accent-default` is not — it's a light, saturated teal that was designed to sit on dark/navy backgrounds (it also doubles as `primary-inverse`), not as text on a near-white background. Fix: either introduce a darker `accent-strong`/`accent-text` token for this one badge tone, or route `status-badge-brand` through `success-default` instead of `accent-default` since the Brand & Style section itself says accent should map to "success-adjacent" moments, not carry text-on-light duty alone.

- **high** `rating` color fails contrast dramatically wherever it renders as text or a small UI indicator (DESIGN.md `rating: '#f59e0b'`, line 51; Colors section line 186) — `#f59e0b` on `surface-raised` white computes to **2.15:1**, far below even the 3:1 non-text/UI-component minimum. If star ratings render as filled icon glyphs at reasonable size this may be a non-issue (large graphical elements have no hard contrast requirement), but if any numeric rating value or outline/unfilled-star stroke uses this hex as text or a thin line against white, it will be close to unreadable for low-vision users. Fix: confirm with the live file/code whether `rating` is ever rendered as text or a thin stroke; if so, supply a darker variant for that use and reserve `#f59e0b` for filled icon fills only.

- **medium** Accessibility Floor's "status is never color-only" claim is true structurally but not validated for contrast (EXPERIENCE.md lines 122–128) — the section correctly defers "visual contrast lives in DESIGN.md," but DESIGN.md's Colors and Components sections never state or verify contrast ratios for any pairing — they describe the soft/strong pattern qualitatively ("soft-background + strong-text pairing") without checking it holds. The two failures above show that deferral left a real gap unflagged. Fix: add a line to the Accessibility Floor explicitly scoping what "color is paired with text" does and doesn't guarantee (presence of text ≠ sufficient contrast), and recommend a contrast-ratio pass across every soft/strong token pair as a named follow-up, not just touch targets and screen-reader labels.

- **medium** RTL/LTR commitment is asserted as a file-structure fact, not framed as independently testable (DESIGN.md lines 176, 225; EXPERIENCE.md lines 126, 20) — the claim "every navigation/chrome component ships RTL and LTR variants in the token file" is a reasonable inference from Figma metadata, but EXPERIENCE.md's own Foundation section notes English/LTR "first-release inclusion unconfirmed" (PRD §9 item 12). That's a direct tension: the Accessibility Floor presents dual-direction support as settled design-system fact while the thing it would ship inside (LTR as a released surface at all) is still an open question upstream. Neither document states what a downstream QA pass should actually check (RTL mirroring of directional icons like back-chevrons and progress indicators, VoiceOver/TalkBack reading order in RTL, bidi handling of mixed Arabic/Latin/numeral strings). Fix: either confirm LTR ships at launch, or add a caveat that the RTL/LTR floor claim applies to the design system's component inventory, not to a confirmed shipping surface, plus name 2–3 concrete RTL behaviors a QA pass should verify.

- **medium** SOS reachability during an active trip is an open accessibility-relevant question, not just a UX one (EXPERIENCE.md Flow 2, step 2, line 147) — the document flags "persistent control vs. behind an overflow menu" as unconfirmed, but doesn't name this as an accessibility concern. For a safety-critical control, burying it in an overflow menu is a motor-impairment and time-critical-use failure independent of labeling or contrast — it needs to be reachable in one or two taps from anywhere in an active trip. Fix: when this is resolved upstream, explicitly require "persistent, not nested" as the accessibility bar for SOS reachability, not just a design preference.

- **medium** Drag-to-reorder has no documented alternative input method (EXPERIENCE.md Interaction Primitives, line 120) — the Driver "Reorder stops" screen is called out as "the one exception to tap-only," rate-limited to 2 edits with a remaining-count indicator, but no keyboard/screen-reader/motor-impaired alternative (e.g., move-up/move-down buttons, or a "Change stop order" list-reorder dialog) is mentioned anywhere. A pure drag gesture with no text-based alternative is inaccessible to screen-reader users and many motor-impaired users by default on both iOS and Android. Fix: confirm whether the live Figma/build has an accessible alternative (up/down affordance) for this one non-tap interaction; if not, flag it as a required addition, not a style choice.

- **medium** Countdown timers have no stated timeout-extension mechanism (EXPERIENCE.md Interaction Primitives, line 118) — OTP resend, payment-offer expiry, cover-request response window, and single-trip offer expiry are all "always rendered as live mm:ss or N minutes text, never a silent timeout," which is good (satisfies "status is never silent"), but nothing addresses WCAG 2.2.1 (Timing Adjustable): is there any way for a user who needs more time — e.g. someone using a screen reader at a slower pace, or with a motor impairment navigating a confirmation flow — to extend a response window before it lapses? This is unaddressed for cover-request (30 min) and single-trip offer windows in particular, where lapsing has real consequences (trip goes uncovered). Fix: confirm whether any of these windows support extension/pause, and if not, flag as a gap for the relevant epics (not necessarily a UX-spine fix, since it may be a backend/business-rule decision).

- **low** Bottom-sheet focus management is unaddressed (EXPERIENCE.md Component Patterns, "Bottom sheet" row, line 93) — every destructive/state-changing sheet is documented as stating consequence copy before the action button (good), but nothing says whether focus moves into the sheet on open and returns to the triggering control on dismiss, which is a standard screen-reader requirement for any modal/sheet pattern. This is exactly the kind of thing static Figma frames can't surface, so it's consistent with the Floor's self-flagged limitation, but it's a specific, nameable gap worth listing for the dedicated accessibility pass the Floor already calls for.

- **low** Day Board "visually distinct" destructive action may rely on styling alone for assistive tech (EXPERIENCE.md Component Patterns, "Day-board action menu" row, line 95) — "Cancel trip always last and visually distinct" has a text label, so it is not color-only in the WCAG sense, but "visually distinct" as the only stated differentiator suggests no mention of a semantic/ARIA distinction (e.g., a destructive role or grouping) for screen-reader users navigating the Admin console's action menu. Fix: when this reaches implementation, pair the visual distinction with a programmatic one (landmark, grouping, or `aria-describedby` warning) so non-sighted admin users get the same "pause before acting" signal.

- **low** Pull-to-refresh has no stated non-gesture alternative on list screens (EXPERIENCE.md Interaction Primitives, line 117) — pull-to-refresh is noted for Student home announcements and trip lists; a manual "Refresh status" button is documented elsewhere (Driver — Pending Review, State Patterns line 107) but not confirmed as present on the pull-to-refresh screens themselves. Motor-impaired users who can't perform a sustained pull gesture need an equivalent tappable control. Fix: confirm an explicit refresh affordance exists alongside pull-to-refresh on every screen that relies on it, not just the one Driver status screen that happens to have one.

- **low** Admin Day Board keyboard navigation is unmentioned (EXPERIENCE.md Admin IA, section G; Flow 4) — the Day Board is described as a dense, interactive dispatch console (ranked driver lists, expandable "Why?" breakdowns, manual override) on a desktop-only, non-responsive 1440×900 frame. Nothing in either document addresses keyboard operability of this interaction-heavy admin surface, which is exactly the kind of component that commonly fails keyboard navigation audits (expandable rows, inline action menus) even when mouse/visual design is solid. Fix: name keyboard operability of the Day Board and other dense Admin tables as a specific item for the dedicated accessibility pass the Floor already calls for.
